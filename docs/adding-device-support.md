# Adding device support

Device support in `aqara_lanlink` is data-driven. Each supported model ships a
per-model package under `custom_components/aqara_lanlink/device/models/<pkg>/`
containing a generated `data.json` (the V3 cloud spec for that model), a
hand-edited `overrides.py` (the correction and extension layer), and a
three-line `__init__.py` shim. The integration reads those packages at startup
and constructs Home Assistant entities from the resulting metadata.

For most contributors, the only file that ever changes is `overrides.py`. The
`data.json` is auto-generated by a maintainer-only catalogue generator that
requires Aqara developer credentials. Contributors do not run the generator;
they improve the quality of what the generator produces.

---

## Which situation am I in?

Work out which tier applies before doing anything else.

**Step 1.** Open [catalogue/index.md](catalogue/index.md) and search for your
device's model string (e.g. `lumi.plug.aeu005`). The index lists every package
in the shipped catalogue.

- If your model string appears in the index, continue to Step 2.
- If it does not appear, go to [Tier C](#tier-c-device-not-in-the-catalogue).

**Step 2.** Open the per-model reference page linked from the index
(`docs/catalogue/by-model/<model_dir>.md`). Check the "Authored traits" table
against what your device actually exposes in Home Assistant.

- If a trait exists in the catalogue and its label, unit, entity type, or
  device class is wrong, go to [Tier A](#tier-a-correct-a-catalogued-trait).
- If a trait that your device physically has is missing entirely from the
  catalogue, go to [Tier B](#tier-b-add-missing-traits-to-a-catalogued-model).

## Tier A: correct a catalogued trait

Use this tier when the device is in the catalogue and an entity is already
appearing in Home Assistant, but something about it is wrong: a label leaked
through untranslated, a unit is incorrect, the entity type should be
`binary_sensor` instead of `sensor`, or the `device_class` needs setting.

The fix goes in the model's `overrides.py`. Locate the file at:

```
custom_components/aqara_lanlink/device/models/<model_dir>/overrides.py
```

`<model_dir>` matches the directory name shown in the catalogue index. The
`OVERRIDES` dict is keyed by wire path (the three-part `A.B.C` string that
identifies a trait in the Aqara V3 protocol). A `TraitSpec` value replaces the
generated entry at that wire path. A `None` value drops the entry entirely so
no entity is created for it.

### Finding the wire path

Open the per-model catalogue page (`docs/catalogue/by-model/<model_dir>.md`).
The wire path is shown in the "Wire path" column of the authored traits table.

### Worked example: fixing an untranslated enum label and forcing a platform

Suppose the catalogue has the occupancy sensor type trait at wire path
`5.160.33001`, but the enum labels are in Chinese and the trait is being
classified as a `select` entity when it should be a read-only `sensor`.

Each entry in `OVERRIDES` must be a complete `TraitSpec` constructed from
scratch. The loader replaces the generated entry at that wire path with your
value. There is no `base` variable available inside `overrides.py`, and
importing the loader module from within it would cause a circular import, so
do not attempt to derive values that way.
The easiest way to get a correct starting `TraitSpec(...)` for any trait is to
run the `aqara_lanlink.export_overlay` service - it emits exactly this shape -
then hand-edit the fields you want to change.

```python
"""Maintainer overrides for this model. Preserved across catalogue regen.
Add entries here for V3 spec corrections, custom device_class, etc.
"""
from custom_components.aqara_lanlink.device.traits import TraitSpec

OVERRIDES: dict[str, TraitSpec | None] = {
    # Correct an untranslated enum label. wire_path is omitted; the loader
    # fills it in from the dict key ("5.160.33001").
    "5.160.33001": TraitSpec(
        id="5.160.33001",
        name="Occupancy sensor type",
        data_type="enum",
        enum_values={
            "0": "PIR",
            "1": "Ultrasonic",
            "2": "Infrared and Ultrasonic",
            "3": "PhysicalContact",
            "4": "Radar",
            "5": "Vision",
        },
        function_code="OccupancySensing",
        trait_code="OccupancySensorType",
        endpoint_id=5,
    ),
    # Force a different Home Assistant entity type / device class:
    #   ... platform="binary_sensor", device_class="motion", ...
    # Drop a generated entry so no entity is created:
    "4.219.20217": None,
}
```

When `wire_path` is omitted from a `TraitSpec`, the loader fills it in from
the `OVERRIDES` dict key automatically. You do not need to set `wire_path`
explicitly.

For a complete reference of every field you can set on a `TraitSpec` and the
rules around illegal field combinations, see [overrides.md](overrides.md).

## Tier B: add missing traits to a catalogued model

Use this tier when the device is in the catalogue but the catalogue missed
traits that your physical device actually exposes. The workflow has two stages:
discover and validate locally using the overlay, then export the result into
`overrides.py` for the PR.

### Stage 1: discover and validate

1. In Home Assistant, go to Developer Tools > Actions and call the
   `aqara_lanlink.scan_device` service against your device:

   ```yaml
   action: aqara_lanlink.scan_device
   data:
     device_id: <your device ID>
   ```

   Use the device picker to find the device ID. The service runs a one-shot
   cloud scan, compares the result against the local catalogue, and reports any
   gaps.

2. Go to Settings > Devices & Services > Repairs. If gaps were found, a repair
   issue named "scan_review" appears. Open it.

3. The repair issue shows a checklist of discovered traits, each with its wire
   path, name, platform, and a sample cloud value where available. All entries
   are pre-selected. Untick any you do not want (for example, internal
   housekeeping traits that should not become entities).

4. Click Fix. The accepted traits are written into the per-install overlay and
   the config entry reloads automatically. The new entities appear in Home
   Assistant.

5. Verify that the new entities behave correctly over a few minutes of normal
   device use. If something looks wrong, you can still adjust the labels and
   platform in the overlay before exporting.

### Stage 2: export and paste into overrides.py

Once the entities look correct, call the `aqara_lanlink.export_overlay` service
to produce a ready-to-paste Python snippet:

```yaml
action: aqara_lanlink.export_overlay
data:
  model: lumi.plug.aeu005   # optional; omit to export all models in the overlay
```

A Persistent Notification titled "Aqara LAN Link overlay export" appears (bell
icon top-right, or Notifications in the sidebar). Its body is a Python block
containing an `OVERRIDES` dict formatted for direct use in `overrides.py`.

Copy the snippet and paste it into the model's
`custom_components/aqara_lanlink/device/models/<model_dir>/overrides.py`,
inside the existing `OVERRIDES` dict. Adjust any labels, units, or platform
values that still need polishing.

The landed artifact is the same `overrides.py` file as Tier A. The overlay is
only a local staging area for discovering and verifying traits before they go
into the PR; it is not submitted directly.

For full details on the scan and export services, see [services.md](services.md).

## Tier C: device not in the catalogue

Catalogue generation requires Aqara developer credentials and is a
maintainer-only step. You cannot generate or add a `data.json` package
yourself.

Open a "New device support" GitHub issue and include:

- The Aqara model string or strings (e.g. `lumi.camera.agl010`,
  `lumi.plug.aeu005`). This is not the marketing name; it is the identifier
  shown in the Aqara app's device settings under "Model" or visible in the
  integration's device info panel.
- The product name as sold (e.g. "Aqara Camera Hub G3").
- Your region (EU, CN, US, etc.).
- The firmware mode (Zigbee, Matter, or Other/Unknown).

A maintainer will regenerate the catalogue to add a `data.json` package for
your model. Once that package ships, you can follow up with an `overrides.py`
polish PR (Tier A) to correct labels or entity types that need adjustment.

## Enabling PTZ for a camera

PTZ (pan/tilt/zoom) operates over a separate local P2P control plane that is
not part of the V3 trait catalogue, so it cannot be enabled through `OVERRIDES`
alone. To enable it for a camera model, add a `CAPABILITIES` dict to the
model's `overrides.py`:

```python
CAPABILITIES: dict[str, frozenset[str]] = {
    "ptz": frozenset({"pan_tilt", "zoom", "presets"}),
}
```

Only declare sub-features the camera actually supports (`pan_tilt`, `zoom`,
`presets`). The PTZ control plane also requires the camera's IP address to be
set in the integration options for that subentry. See [ptz.md](ptz.md) for the
full protocol details and what each sub-feature enables in Home Assistant.

## Submitting your PR

1. Open (or link to) the New Device Support issue for the model you are
   improving. The issue gives reviewers context and lets others find the work.

2. Edit the model's
   `custom_components/aqara_lanlink/device/models/<model_dir>/overrides.py`
   with your corrections or additions.

3. Run the test suite to confirm nothing is broken:

   ```
   python3 -m pytest tests/ -v
   ```

4. Open a pull request. In the PR description, reference the issue with
   `Closes #<issue number>` and briefly describe what changed (which traits
   were corrected or added, and why). Follow the `.github` PR template if one
   is present.

For the full PR process - branching conventions, review expectations, and CI
requirements - see [../CONTRIBUTING.md](../CONTRIBUTING.md).
