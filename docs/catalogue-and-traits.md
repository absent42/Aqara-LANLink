# Catalogue and traits

This document is the shared vocabulary reference for the Aqara LANLink integration's device-support data model. Other documents - [architecture.md](architecture.md), [overrides.md](overrides.md), [adding-device-support.md](adding-device-support.md), and the [per-model reference library](catalogue/README.md) - link here instead of re-explaining these terms.

Device support is data-driven. Every supported device model ships a per-model package that describes which traits the device exposes, what types they are, and how they map to Home Assistant entities. The integration reads those packages at startup and constructs entities from the resulting metadata. No model-specific logic lives in the platform code.

---

## The per-model package

Each supported model has a package directory under `custom_components/aqara_lanlink/device/models/<model_id>/` containing exactly three files.

**`data.json`** is auto-generated by the catalogue generator from Aqara's V3 Open Cloud spec. It contains all trait metadata, endpoint layout, and device classification data for the model. Maintainers do not edit this file by hand; it is regenerated whenever the upstream spec is refreshed. Any corrections made directly to `data.json` will be overwritten on the next regeneration.

**`overrides.py`** is the hand-edited correction layer. It exports a single dict, `OVERRIDES: dict[str, TraitSpec | None]`, keyed by wire path. An entry whose value is a `TraitSpec` replaces the corresponding generated entry at that wire path. If the `TraitSpec` is written without a `wire_path` field set, the loader (`device/models/_loader.py`) auto-fills it from the `OVERRIDES` dict key via `dataclasses.replace(spec, wire_path=wp)`. This is load-bearing: subscribe/seed and report routing are both keyed on `wire_path`, so an override that left it unset would otherwise be silently skipped. Authors may therefore omit `wire_path` from an override and rely on the dict key to supply it. An entry whose value is `None` removes the generated entry entirely. A new wire-path key that does not appear in `data.json` introduces a brand-new trait. The overrides file survives catalogue regeneration; it is the right place for V3 spec corrections, custom `device_class`, adjusted `entity_category`, and similar per-model tweaks. See [overrides.md](overrides.md) for the full authoring rules.

**`overrides.py`** may also export an optional `CAPABILITIES` dict alongside
`OVERRIDES`. `CAPABILITIES` declares off-catalogue capabilities - features that
the V3 trait catalogue does not cover, such as PTZ (pan/tilt/zoom). The model
loader reads it and indexes it in the registry. See [ptz.md](ptz.md) for
context on why PTZ requires this mechanism, and [overrides.md](overrides.md)
for the `CAPABILITIES` dict format.

**`__init__.py`** is a three-line shim that calls `load_model_data(Path(__file__).parent)` and populates the package namespace via `globals().update(...)`. It is also auto-generated and must not be edited.

The loader (`device/models/_loader.py`) reads `data.json`, constructs a `TraitSpec` for every wire path in `traits`, then applies the overrides on top. The merged result is what the rest of the integration sees.

## What a data.json contains

`data.json` is a flat JSON object. Its top-level fields are:

- **`model`** - the single canonical/primary model identifier for this package, e.g. `"lumi.camera.agl010"`. This is distinct from `models`: it is the one authoritative id used as the package key, whereas `models` is the full tuple of model strings the package covers (which may include whitelabel or SKU variants).
- **`models`** - list of Aqara model identifiers (typically one, but a package can cover multiple SKUs that share an identical spec).
- **`manufacturer`** - display-name string for the manufacturer, e.g. `"Aqara"`.
- **`display_name`** - human-readable model name, usually the primary model identifier string.
- **`regions`** - list of region codes in which the model is sold, e.g. `["eu", "cn"]`. Empty list means the spec did not specify regions.
- **`bundle_ids`** - list of Aqara bundle/app identifiers associated with this model. Used for whitelabel resolution.
- **`endpoints`** - mapping of integer endpoint id (as a string key) to an object containing at least a `deviceType` field, e.g. `{"2": {"deviceType": "Camera"}}`.
- **`device_types`** - flat list of all unique `deviceType` strings across all endpoints on this model.
- **`traits`** - the main payload: a mapping of wire path to a dict of `TraitSpec` fields (excluding `id` and `wire_path`, which are inferred from the key).
- **`dropped_paths`** - list of V3 wire paths that the catalogue generator encountered but classified as drop. These paths are known to the integration and are silently consumed when the hub pushes them, rather than surfacing as unknown-path candidates. They do not produce entities.
- **`whitelabels`** - mapping of model identifier to display name for rebranded variants that share this package's spec.
- **`source_region`** - the region code whose V3 spec was used when generating this package, e.g. `"ger"` or `"cn"`.

### Trimmed example - `camera_agl010/data.json`

The camera agl010 is a good illustration because it has multiple endpoints spanning different detection capabilities.

```json
{
  "models": ["lumi.camera.agl010"],
  "manufacturer": "Aqara",
  "display_name": "lumi.camera.agl010",
  "source_region": "ger",
  "regions": [],
  "bundle_ids": [],
  "endpoints": {
    "0": {"deviceType": "Root"},
    "1": {"deviceType": "Public"},
    "2": {"deviceType": "Camera"},
    "3": {"deviceType": "HumanDetector"},
    "5": {"deviceType": "MotionSensor"},
    "6": {"deviceType": "PetMonitor"},
    "7": {"deviceType": "SoundSensor"}
  },
  "device_types": ["Camera", "HumanDetector", "MotionSensor", "PetMonitor", "Public", "Root", "SoundSensor"],
  "traits": {
    "1.171.20119": {
      "endpoint_id": 1,
      "function_code": "NetworkCommissioning",
      "trait_code": "WiFiRSSI",
      "name": "Wi fi RSSI",
      "data_type": "int",
      "min_value": -100.0,
      "max_value": 0.0,
      "step": 1.0,
      "subscribable": true,
      "entity_category": "diagnostic",
      "default_enabled": false
    },
    "5.160.33000": {
      "endpoint_id": 5,
      "function_code": "OccupancySensing",
      "trait_code": "Occupancy",
      "name": "Occupancy",
      "data_type": "bool",
      "subscribable": true
    }
  },
  "dropped_paths": ["0.128.32896", "..."],
  "whitelabels": {}
}
```

The trait dict key (`"1.171.20119"`, `"5.160.33000"`) is the wire path. The `endpoint_id` field inside each trait object redundantly carries the first component of the wire path to make endpoint-filtered queries cheaper.

## TraitSpec

`TraitSpec` (defined in `device/traits.py`) is a frozen dataclass that holds all metadata about a single trait. The loader constructs one `TraitSpec` per wire path from the fields in `data.json`, with `id` and `wire_path` both set to the dict key.

### Core identity fields

- **`id`** - the canonical trait identifier. For V3 catalogue-generated traits this is identical to `wire_path`. Used as the key in the runtime trait catalog (`BY_ID`).
- **`name`** - human-readable label, e.g. `"Occupancy"` or `"Wi fi RSSI"`. Auto-generated from the cloud spec.
- **`wire_path`** - the dotted-numeric address used on the LANLink wire, e.g. `"5.160.33000"`. This is different from the dotted-numeric resource IDs shown in the Aqara API documentation. See the wire paths section below.
- **`data_type`** - one of `"bool"`, `"int"`, `"float"`, `"enum"`, `"string"`, `"unknown"`. Drives entity-platform selection in the fallback composer.
- **`unit`** - raw unit string from the V3 spec, e.g. `"°C"`, `"lux"`, `"mired"`. May be `None`.
- **`enum_values`** - for `data_type="enum"`, a `dict[str, str]` mapping string integer keys to display labels, e.g. `{"0": "PIR", "1": "Ultrasonic"}`.
- **`min_value`**, **`max_value`**, **`step`** - numeric bounds for `int` and `float` traits. All three are `float | None`.
- **`readable`** - whether the trait can be read on demand. Defaults to `True`.
- **`writable`** - whether the trait accepts write commands. Defaults to `False`. The fallback composer routes writable enum traits to `SelectDescriptor`, writable numeric traits to `NumberDescriptor`, and writable bool traits to `SwitchDescriptor`.
- **`subscribable`** - V3 flag indicating the hub will push unsolicited updates for this trait.
- **`default_enabled`** - whether the resulting entity is enabled in Home Assistant by default. `False` means the entity is created but disabled until the user explicitly enables it.

### V3 catalogue fields

- **`function_code`** - the V3 cluster/function grouping, e.g. `"OccupancySensing"`, `"Camera"`, `"BasicInformation"`. Together with `trait_code` this is the primary key used by the trait policy and the composers to identify what a trait does.
- **`trait_code`** - the V3 trait name within its function, e.g. `"Occupancy"`, `"WiFiRSSI"`, `"CurrentLevel"`.
- **`endpoint_id`** - integer endpoint the trait belongs to. Redundant with the first component of `wire_path` but carried explicitly for filtering.

### Override-relevant classification fields

These fields have no effect when the auto-generated value is acceptable, but are the primary reason an `overrides.py` entry exists for a trait.

- **`platform`** - explicit Home Assistant entity platform, e.g. `"sensor"`, `"binary_sensor"`, `"switch"`, `"number"`, `"select"`, `"event"`, `"button"`. When `None` the composer infers a platform from `data_type` and `writable`. Setting this in an override forces a specific platform. Valid values are enforced at construction time; an invalid value raises `RuntimeError`.
- **`entity_category`** - `None`, `"config"`, or `"diagnostic"`. Enforced at construction time.
- **`device_class`** - Home Assistant device class string, e.g. `"motion"`, `"temperature"`, `"battery"`.
- **`state_class`** - Home Assistant state class for sensors, e.g. `"measurement"`. Requires `platform="sensor"` or construction raises `RuntimeError`.
- **`unit_of_measurement`** - the unit displayed in HA, which may differ from the raw wire `unit` when a `scale` conversion is applied. Requires `platform` in `{"sensor", "number"}`.
- **`scale`** - multiplicative factor applied to the raw wire value before it is reported to HA, e.g. `0.01` to convert centidegrees to degrees. Must be a non-zero finite float. Requires a numeric platform.
- **`suggested_display_precision`** - decimal places hint for HA's entity display.
- **`icon`** - a Material Design Icons string, e.g. `"mdi:motion-sensor"`, that overrides the default icon Home Assistant would infer from `platform` and `device_class`. When `None` (the default) HA picks the icon automatically. Setting this in an override is useful when the inferred icon is misleading or absent.
- **`auto_clear_seconds`** - for `platform="binary_sensor"` only: the entity automatically resets to `False` this many seconds after the last `True` push, for momentary-event traits like motion. Must be a positive finite float.

Construction-time validation enforces legal field combinations across all of these fields. Refer to [overrides.md](overrides.md) for the override-specific rules and worked examples.

## Wire paths, trait ids, endpoints, and deviceTypes

### Wire path

A wire path is a three-component dotted-numeric string in the form `<endpoint_id>.<function_id>.<property_id>`, for example `5.160.33000`. It is the address the LANLink protocol uses when the hub reports or accepts a trait value. These are different to the 
three-component dotted-numeric resource IDs shown in the Aqara API documentation and 
are not directly intechangable.

- The first component is the **endpoint id** (an integer, `0`-based).
- The second component is the **function id** (integer, maps to a `function_code` like `OccupancySensing = 160`).
- The third component is the **property id** (integer, maps to a `trait_code` like `Occupancy = 33000`).

Wire paths are the primary key in `data.json`'s `traits` dict and in `overrides.py`'s `OVERRIDES` dict.

### Trait id

In the V3 catalogue every trait's `id` is set equal to its `wire_path` by the loader. The distinction matters for the runtime trait catalog (`BY_ID` in `device/traits.py`), which is keyed by `id`: if two models expose the same `(function_code, trait_code)` pair on different endpoints, the resulting `TraitSpec` objects have different `id` / `wire_path` values and are stored as separate catalog entries.

### Endpoints and deviceTypes

A device exposes one or more **endpoints**, each with a **deviceType** string. Endpoints are the primary decomposition unit: the `Camera` endpoint on endpoint 2 carries camera-related traits, the `MotionSensor` endpoint on endpoint 5 carries motion traits, and so on. The `endpoints` field in `data.json` maps endpoint id to `{"deviceType": "..."}`.

At classification time (`classify_v3.py`), traits are grouped by their `endpoint_id`, then each group is handed to the composer registered for that endpoint's deviceType. This means a single physical device can produce entities of very different kinds - a camera stream entity from endpoint 2 and a motion binary sensor from endpoint 5 - all from one per-model package.

Each per-model package's `device_types` list is the flat union of all `deviceType` strings across its endpoints. It is used for quick membership checks before the per-endpoint dispatch.

## Composers

A **composer** is a Python function in `device/device_types/` that accepts a filtered trait dict for one endpoint and returns a list of `AnyDescriptor` objects. Each descriptor becomes one Home Assistant entity. The composer for a given deviceType encodes the mapping rules: which traits become which entity types, what the entity is named, which fields are required.

Composers live in files named after their deviceType, for example `device/device_types/light.py`, `device/device_types/camera.py`, `device/device_types/occupancy_sensor.py`. A fallback composer handles deviceTypes not covered by a dedicated file by routing each trait individually based on `data_type` and `writable`.

### The fused Light composer

The `Light` deviceType is handled by a fused composer. It merges multiple traits from the same endpoint into a **single** `LightDescriptor`:

- `Output.OnOff` (required) becomes the power control.
- `LevelControl.CurrentLevel` (optional) adds brightness control.
- `ColorControl.ColorTemperature` (optional) adds color temperature control, with automatic mired-to-Kelvin conversion.
- `ColorControl.ColorXY` or the `CurrentX`/`CurrentY` pair (optional) adds XY color control.

All other traits on a Light endpoint (transition times, scene presets, startup mode, music sync, etc.) pass through to the fallback composer and become their own entities.

Because the fused composer merges traits that cannot be cleanly separated, **per-trait `platform` overrides are ignored on Light endpoints**. If an override sets `platform` on a trait that the Light composer absorbs, the integration logs a warning and the override has no effect. This limitation does not apply to single-trait-absorbing composers (such as camera detector composers) or pure passthrough composers, which do honor per-trait platform overrides.

## trait_policy: visible / diagnostic / drop

`device/trait_policy.py` is the single source of truth for which `(function_code, trait_code)` pairs are kept, hidden by default, or excluded entirely. The catalogue generator consults this policy when building `data.json`; the runtime classifier (`classify_v3.py`) consults it again at startup.

**visible** - the trait produces an entity that is enabled by default on the device card. This is the default classification for any `(function_code, trait_code)` that is not explicitly listed elsewhere.

**diagnostic** - the trait produces an entity but it carries `entity_category="diagnostic"` and is disabled by default. Users can enable diagnostic entities manually. Examples: WiFi RSSI, battery voltage, camera active status.

**button** - the trait produces a `ButtonDescriptor` (a press-to-trigger entity). Currently no traits are classified as button.

**drop** - the trait is excluded entirely. No `data.json` entry is written and no entity is created. Dropped classifications cover administrative noise (ZCL/Matter network diagnostics, static device-registry fields like serial number and vendor name), protocol plumbing with no HA utility, and any path the maintainer has decided is out of scope.

### dropped_paths in data.json

`dropped_paths` is the list of wire paths that were present in the V3 spec for this model and were classified as drop by `trait_policy`. Storing them explicitly serves an operational purpose: when the hub pushes a value for a dropped path at runtime, the integration can silently consume it rather than logging it as an unknown path. This keeps the logs clean on devices with large trait surfaces.

Dropped paths typically include such things as device endpoint icons in the Aqara app, and internal diagnostic values such as Zigbee network neighbours.

`dropped_paths` is distinct from overrides where `None` is set. A `None` override in `overrides.py` removes a trait that was *not* classified as drop by policy - typically because the generated entry is incorrect or premature. Paths in `dropped_paths` were correctly classified as drop at generator time and never made it into `traits` at all.

## Glossary

**hub** - the Aqara hub device (e.g. M2, M3, E1) that the integration connects to over the local network. All sub-device communication passes through the hub.

**sub-device** - a Zigbee or Matter device paired to the hub, e.g. a motion sensor, a bulb, a door lock. Sub-devices are addressed by their DID.

**DID** - device identifier, a string assigned by Aqara that uniquely identifies a hub or sub-device on the Aqara platform.

**trait** - a single addressable property of a device, described by a `TraitSpec`. Examples: `Occupancy`, `CurrentLevel`, `WiFiRSSI`.

**wire path** - the three-part dotted-numeric address (`<endpoint>.<function>.<property>`) used in LANLink protocol messages to identify a specific trait value, e.g. `5.160.33000`.

**trait id** - the canonical string key used to look up a `TraitSpec` in the runtime catalog. In the V3 catalogue this equals the wire path.

**endpoint** - a logical sub-unit of a device, carrying a `deviceType` label and a subset of the device's traits. A device may have multiple endpoints representing different functional roles (camera, motion detector, sound detector, etc.).

**deviceType** - the type label assigned to an endpoint, e.g. `"Light"`, `"Camera"`, `"MotionSensor"`. Determines which composer handles that endpoint's traits.

**composer** - a Python function in `device/device_types/` that converts a filtered set of traits (one endpoint's worth) into a list of Home Assistant entity descriptors.

**descriptor** - a dataclass instance (e.g. `LightDescriptor`, `BinarySensorDescriptor`) that captures everything needed to register one Home Assistant entity. Produced by composers, consumed by the platform setup code.

**overlay** - runtime state updates layered onto a descriptor's base attributes. Not to be confused with overrides.

**override** - a hand-authored `TraitSpec | None` entry in a model's `overrides.py` that corrects or replaces the auto-generated trait metadata for a specific wire path. Survives catalogue regeneration. See [overrides.md](overrides.md).

**TraitSpec** - the frozen dataclass (`device/traits.py`) that holds all metadata for one trait: identity, data type, bounds, V3 catalogue codes, and optional HA classification fields.
